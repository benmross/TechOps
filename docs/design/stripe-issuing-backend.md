# Stripe Issuing backend

The finance backend persists virtual-card requests in MongoDB and connects to
Stripe Issuing through the official Node SDK, pinned to 23.1.0. Its default API
version and the Issuing Elements ephemeral-key version are 2026-10-28.endive.
The existing React Finance preview remains a separate in-memory demonstration;
it does not call these endpoints yet.

## Configuration

Finance is disabled unless PEOPLEPORTAL_FINANCE_ENABLED=true. This release
accepts only sk_test_ or rk_test_ keys and rejects live Stripe objects. Do not
configure live credentials. There is no live-mode enable switch.

Set these in the server's private environment, never in source control:

| Variable | Purpose |
| --- | --- |
| PEOPLEPORTAL_FINANCE_ENABLED | Set to true to enable the test integration |
| STRIPE_SECRET_KEY | Stripe Issuing sandbox secret or restricted test key |
| STRIPE_WEBHOOK_SECRET | Signing secret for this endpoint, not an API key |
| PEOPLEPORTAL_FINANCE_REVIEWER_PKS | Comma-separated numeric directory user PKs allowed to review |
| PEOPLEPORTAL_FINANCE_ORIGIN | Exact browser origin, for example https://portal.example.com |

MongoDB must be a replica set (a single-node development replica set is enough)
or a transaction-capable managed cluster. Approval changes the request, shared
budget and audit record in one transaction. Startup checks transaction support
when enabled. A standalone MongoDB must be upgraded to a replica set before
enabling finance; it must not fall back to nontransactional approvals.

The new collections are additive. There is no migration of the sample UI data,
which has never been durable. Startup creates required unique indexes and a
zero-dollar USD test allocation ceiling. Nothing is funded or issued at startup.
The original chart checkout and its development server are independent.

## Access and workflow

All API routes except the signed webhook require the existing OIDC session.
The backend reloads the user from Authentik and checks active/current status.
Every write requires JSON and an exact configured Origin header. Use the normal
authenticated browser session, not a role selector from the demonstration UI.

Finance review authority comes only from the operator-configured reviewer PK
allowlist. Team ownership, executive status and technical administration do not
implicitly grant finance rights. A requester cannot approve their own request.
The requester is also the card custodian. Creation, approval, issuance and
card-detail access check current membership of the selected active subteam and
verify that it belongs to the selected root team.

Finance first onboards the individual in the Stripe sandbox, resolving any
requirements and accepting terms through the appropriate human workflow. Then
finance maps that Stripe cardholder ID to the directory user's PK. This backend
does not fabricate addresses, identity information or terms acceptance. Mappings
are unique and immutable through the API. Changing one requires a reviewed data
migration. The mapping is pinned to a request at approval.

## API

Routes are generated by tsoa and included in the existing OpenAPI documentation.
Amounts are integer USD cents. Request IDs are Mongo ObjectIds. List responses
contain at most 50 requests, newest first; pass the last ID as before to continue.
Request detail includes the latest 100 normalized entries and audit events;
the returned spending totals aggregate all stored entries.

| Method and path under /api/finance | Body or behavior |
| --- | --- |
| POST /requests | rootTeamPk, subteamPk, purpose, vendor, requestedCents, interval, neededUntil, clientRequestId |
| GET /requests?before=... | Own requests; reviewers can see all |
| GET /requests/{id} | Request, settled/held totals, recent ledger entries and audit |
| POST /requests/{id}/approve | approvedCents and note; reserves allocation, queues issuance |
| POST /requests/{id}/decline | note; pending requests only |
| PUT /requests/{id}/card-status | status: active, inactive (freeze), or canceled |
| POST /requests/{id}/reconcile | Reviewer-triggered issuance/recovery and spending refresh |
| POST /requests/{id}/ephemeral-key | Stripe.js nonce; custodian only; no-store response |
| GET /budget | Reviewer view of totalCents and reservedCents |
| PUT /budget | totalCents; cannot go below existing allocations |
| PUT /cardholders/{userPk} | stripeCardholderId; reviewer-only mapping |
| POST /webhook | Raw Stripe-signed JSON; no session or Origin requirement |

For example, a request body is:

```json
{
  "rootTeamPk": "root-team-directory-pk",
  "subteamPk": "subteam-directory-pk",
  "purpose": "Project hosting",
  "vendor": "Hosting vendor",
  "requestedCents": 10000,
  "interval": "all_time",
  "neededUntil": "2026-12-01T00:00:00Z",
  "clientRequestId": "88c32845-a97d-4eb4-842c-aa2a39844545"
}
```

Reuse the UUID and identical payload when retrying request creation. A changed
payload with the same UUID returns a conflict. Approvals are single transitions,
including under concurrent requests. A partial approval preserves requestedCents.

## Allocation accounting

The configured budget is a conservative program allocation ceiling, not a copy
of the Stripe Issuing balance and not proof that Stripe is funded. Finance must
fund the test Issuing balance separately. An insufficient Stripe balance can
still cause authorizations to be declined.

One-time cards use an all_time spending limit and reserve the approved amount.
Monthly cards reserve the full approved amount for every UTC calendar month
touched between approval and neededUntil, including both endpoint months. A date
must be in the future and within 366 days. This bounds recurring commitments
instead of promising an indefinitely renewable allocation from one month's cash.

Freeze, cancellation, expiry and refunds do not automatically release an approved
allocation. This deliberately favors under-allocation over reusing money that
could still be captured later. Uncertain issuance also retains the reservation.
Automated budget recycling, receipts, approved increases and period-based budget
reporting are not implemented. Finance can raise the total ceiling after review;
the API cannot silently discard committed allocations.

Stripe spending controls are not an isolated prepaid balance. Stripe documents
aggregation delays up to 30 seconds and later tips/fees that can exceed limits.
The vendor field records the requested purpose; it does not enforce a merchant
allowlist. Real-time authorization policy and merchant-ID restrictions are not
implemented in this release. Do not subscribe to issuing_authorization.request
for this webhook; use Stripe's configured authorization behavior and controls.

## Issuance, reconciliation and recovery

Agenda polls every 30 seconds when finance is enabled. The finance maintenance
job is scheduled each minute and processes up to 50 due requests, with a five
minute reconciliation interval per request. Status changes are queued; the
response reports desired and observed card statuses separately. A reviewer can
request reconciliation immediately. Expiry is a scheduled cancellation, with
worker/queue delay, not an exact wall-clock authorization guarantee.

Workers acquire a per-request five-minute lease. Cards are created inactive
with a persisted request-specific Stripe idempotency key and request-ID metadata.
The card ID is saved before activation. Retrying after a lost response uses the
same key. After 23 hours, workers search that cardholder's cards for matching
metadata instead of blindly replaying a key Stripe might have evicted after
24 hours. If recovery finds nothing, the request stays reserved and needs a
manual Stripe investigation. Review failures through needsAttention and the audit
trail. Raw SDK errors and whole Stripe objects are not persisted or returned.

Current directory failures block new issuance; an existing card is frozen if
membership cannot be verified. Removed members are not issued new cards. Cards
whose end date has passed are canceled; canceled cards cannot be reactivated.
Keep the worker running for expiry and membership enforcement.

Subscribe the endpoint to issuing_card.created, issuing_card.updated,
issuing_authorization.created, issuing_authorization.updated,
issuing_transaction.created and issuing_transaction.updated. Use the same
Stripe API version as the SDK. For local testing, forward those events with the
Stripe CLI to the separate test backend's /api/finance/webhook route and configure
the signing secret from that specific listener.

The webhook is mounted before express.json and session middleware, verifies the
raw bytes using the SDK and rejects live events. It records each event ID once
inside a transaction. It fetches current Stripe state rather than treating webhook
delivery order as authoritative. Normalized entries are upserted by Stripe object
ID; duplicate deliveries cannot add spend twice. Periodic full pagination repairs
missed webhooks, including for expired cards. Unrecognized cards are ignored and
later polling recovers events delivered before the local card ID was saved.

Pending approved authorizations are held separately from settled transactions.
Closed, reversed or declined authorizations no longer contribute a hold.
Transaction amounts are Stripe balance deltas: captures are negative and refunds
positive. Settled spending is their negated sum. This is a spending view, not a
complete financial ledger of Issuing fees, disputes or funding movements.

Card details use the Stripe Issuing Elements nonce exchange, authorized only for
the current custodian. PAN and CVC never pass through this backend. The endpoint
returns a short-lived ephemeral secret directly to the browser with no-store and
records only the access action, never the nonce or secret.

## Verification

Use Node 22 and run npm exec nx run pplserver:test. Finance integration tests use an isolated
MongoDB replica set, the real generated routes and SDK signature verification,
and an injected Stripe transport. They cover concurrency, authorization, request
idempotency, uncertain issuance, partial approvals, expiry, freezes, membership
changes, event deduplication, refunds and raw-body tampering. No test calls a live
Stripe account or needs real keys. A real Issuing sandbox check is a separate
step after credentials, account capabilities and test cardholder setup exist.
